Case Study: RFI PDF Data Extraction & Log Automation Across Four Packages

A live multi-package construction programme. Four packages — referred to here as C1, B1, B2 and C2 — four different contractors, four different Request-for-Inspection forms, and four Excel registers that had grown to 19,326 RFI rows across 13 sheets. Client, project and contractor identities are withheld; the package codes shown are generic labels used for illustration only.

The problem

Every returned RFI PDF was being read by hand and typed into a shared register — RFI number, revision, discipline, location, submission date, the engineer's stamped decision and approval date, several hundred times a month. The register carried the client's agreed layout: logos, dropdowns, colour-coded status rules and cross-sheet summary formulas. Rebuilding it was not an option, and one careless paste could break the colour-coding across roughly 15,000 rows. Management still had no reliable weekly picture of what was submitted, approved, rejected or ageing past SLA.

What was built

A single self-contained offline HTML tool. Double-click it, drop in the existing log and a folder of RFI PDFs, review what it read, and save. No installation, no internet connection, no data leaving the machine.

  • Reads the RFI number, revision, discipline, location/chainage, dates, times and the engineer's stamped decision straight off the PDF.
  • Classifies every PDF automatically as new RFI, new revision of an existing one, or already logged — a revision is inserted directly under its parent, and an already-logged PDF updates only the status instead of creating a duplicate row.
  • Writes into the existing workbook, editing only the rows involved.
  • Decisions arriving without a PDF — by email or at a site meeting — are queued and written through the same path.
  • Builds a management dashboard inside the workbook, plus a shareable weekly report.
Why it did not break the register

The workbook is opened as the archive it actually is, and only the specific worksheet rows involved are edited — everything else is carried through byte-for-byte. Verified on every save:

  • 10,190 conditional-formatting rules and 107 dropdown validations preserved.
  • Logos, printer settings, drawings, print areas, merged cells and cross-sheet total formulas intact.
  • Row inserts reflow every affected reference — cell formulas, conditional-formatting ranges, data validations and filters.
  • COUNTIF summary blocks sitting a few rows below the data are pushed down rather than overwritten.
  • A timestamped backup is downloaded before any save, and a preview shows the exact sheet, row and column of every change.
Adapting to four different contractors — without hard-coding anything

The four packages were genuinely different, and each difference would have silently corrupted data had it been assumed away:

Varies by package C1 B1 B2 C2
RFI number shape 5 parts, with area 4 parts 4 parts 4 parts
Revision separator space / underscore mixed, all three space / underscore underscore / hyphen
Status column J J I J
Approval-date column I I H I
Where work happens 4–5 areas pipeline chainage pipeline chainage single site

Column layout is detected per sheet from its own header row rather than assumed — one package's approval dates would otherwise have been written into its Location column, and that layout varies within a workbook, not only between them. Every row and every PDF carries its package inside its own number, so routing needs no guesswork from folder names. A fifth package needs no code change.

What the pre-flight check found in the live register

Before adding anything, every load reports — read-only — what is already wrong in the log. On the production file it surfaced problems that had been invisible for years:

  • 8,632 numbers at risk of a silent mis-match — sequence numbers of 5 and 6 digits were being truncated to 4 by an earlier parser, and every one of those truncations collided with a different, real RFI.
  • 22 malformed RFI numbers counted in the totals but invisible to matching — each one a future duplicate row waiting to happen.
  • 53 same-sheet duplicate rows, 18 of which disagreed with each other about the status.
  • 342 rows spelled B- Status instead of B-Status — counted as pending by the workbook's own summary formulas, understating decision activity by 341 events.
  • A broken cross-sheet Total sheet: #REF! rows, one discipline pointing at another's sheet, and a "submitted" cell resolving to a date rather than a count.
  • Remaining append capacity on each sheet before its summary block — one sheet had only 7 free rows left before a batch would have overwritten live formulas.
The management dashboard
  • Completion — by unique RFI number; an RFI counts as done only when its latest revision is accepted.
  • Decision activity — by status event, so rework is visible: one RFI can contribute several rejections plus a final approval.
  • Quality & ageing — first-pass approval rate, undecided RFIs banded 0–3 / 4–7 / 8–14 / 15–30 / 30+ days, SLA breaches by discipline, the oldest undecided RFI, and a completion forecast projected from the recent approval run-rate.
  • Repeated-approval flags carrying the full Rev.0 rejected → Rev.1 code-B → Rev.2 accepted trail behind each one.
  • Filter to a single package or view all four combined; weekly windows end on and include the data date.
How it was verified
  • End-to-end against the real production file — 13 sheets, 19,326 rows.
  • 63 unit tests covering date, time, status and RFI-number parsing.
  • Every dashboard figure independently recomputed from the raw workbook and compared against the tool's output.
  • Write tests: a batch overrunning a sheet's headroom, a mid-sheet revision insert, a status-only update, a full derived-column back-fill and a status normalisation.
  • An independent checker script diffs the loaded file against the saved file and reports anything that changed which should not have.
  • PDF field extraction verified on 87 real PDFs across all four contractors' forms.
